    Import from `firebase/firestore`: `collection`, `addDoc`, `serverTimestamp`, `query`, `orderBy`.

    Define a TypeScript interface `LogEntry`:
    ```
    interface LogEntry {
      trackableId: string
      timestamp: ReturnType<typeof serverTimestamp>
      loggedBy: string
      note?: string
    }
    ```

    Export a `logsCollection` function that returns the Firestore collection ref for a given subject:
    ```
    export function logsCollection(subject: string) {
      return collection(db, 'subjects', subject, 'logs')
    }
    ```

    Export an `addLog` async function:
    ```
    export async function addLog(subject: string, trackableId: string): Promise<void> {
      const entry: LogEntry = {
        trackableId,
        timestamp: serverTimestamp(),
        loggedBy: 'caregiver',
      }
      await addDoc(logsCollection(subject), entry)
    }
    ```
    Note: `loggedBy` is hardcoded to `'caregiver'` for Phase 1 (the Me/Wife picker is Phase 2 per LOG-02). The `note` field is not included in Phase 1 writes but is present in the TypeScript interface per D-05 to avoid a schema migration.

    Step 2 — Create firestore.rules in the repo root:

    ```
    rules_version = '2';
    service cloud.firestore {
      match /databases/{database}/documents {
        match /subjects/{subject}/logs/{logId} {
          allow read, write: if request.auth != null;
        }
      }
    }
    ```

    This satisfies INFRA-03: all Firestore reads and writes require `request.auth != null`.
    The wildcard `{subject}` satisfies TRACK-02: the rules work for any subject, not just "madgy".
    The default-deny behavior of Firestore rules means anything NOT matching is automatically denied.

    Read the existing firebase.json. Add a `"firestore"` key alongside `"hosting"`:

    ```json
    }
    ```

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Browser (anonymous user) → Firestore | Firestore write from anonymous auth session; auth token required |
| Second browser → Firestore listener | onSnapshot subscription; auth token required |
| Firestore rules → REST API | Unauthenticated REST reads/writes must be denied |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-02-01 | Elevation of Privilege | Firestore write without auth | mitigate | `firestore.rules`: `allow read, write: if request.auth != null` — unauthenticated callers denied; anonymous auth token is required (INFRA-03) |
| T-02-02 | Elevation of Privilege | Firestore write before auth resolves | mitigate | `addLog()` is only callable after `onAuthStateChanged` fires with a user; Firestore SDK rejects writes if auth is not initialized, and `firestore.rules` provides a second layer of enforcement |
| T-02-03 | Tampering | Forged `loggedBy` value in write | accept | Phase 1 hardcodes `loggedBy: 'caregiver'`; no user-supplied input goes into this field. Phase 2 will introduce a picker but no free-text input. |
| T-02-04 | Denial of Service | Firestore listener left open | accept | Single-page app; listener is cleaned up on component unmount via the unsubscribe return value. Low-risk for a two-user tool. |
| T-02-SC | Tampering | npm packages installed in this phase | mitigate | No new packages installed in this plan — all deps installed in Plan 01. No install tasks here. |
</threat_model>
